## Abstract

This project presents a simulation-only Internet of Things platform for smart campus monitoring. Instead of using physical sensors and hardware boards, the system uses Python virtual devices to generate realistic telemetry from campus rooms. The simulated devices publish data to an MQTT broker using a structured topic hierarchy. A Python subscriber receives the data, validates the payload, calculates derived analytics values, and prints alerts for abnormal conditions. A Node-RED Dashboard flow is provided to visualize latest temperature, humidity, occupancy, alerts, and temperature trends.

The selected wireless communication model is IEEE 802.15.4 / Zigbee-like because smart campus sensors commonly send small periodic messages and benefit from low-power communication. The simulator includes packet loss, random delay, RSSI, link quality, estimated energy consumption, and battery drain to make the communication model more realistic. The final result demonstrates a complete IoT workflow: device simulation, wireless behavior modeling, MQTT publish/subscribe, analytics processing, dashboard visualization, testing, and documentation.

## Problem Statement and Scenario

University campuses include many spaces that require continuous monitoring. Classrooms need acceptable temperature and lighting levels. Laboratories may require air quality monitoring. Offices can benefit from occupancy-based energy saving. Server rooms need fast detection of high temperature because overheating can damage equipment.

Building a physical IoT prototype requires sensors, microcontrollers, power supplies, wiring, and network setup. This can be difficult for a course project when the main learning objective is to understand IoT architecture, communication, data processing, and visualization. Therefore, this project uses software simulation only.

The project scenario is a smart campus with four monitored rooms:

| Device ID | Building | Room | Main Monitoring Purpose |
|---|---|---|---|
| classroom_101 | main_building | classroom_101 | Comfort and occupancy monitoring |
| lab_201 | engineering_building | lab_201 | Lab comfort and air quality monitoring |
| office_301 | admin_building | office_301 | Energy saving and occupancy monitoring |
| server_room_401 | it_building | server_room_401 | Temperature risk monitoring |

Each room has one virtual IoT device. The device sends telemetry every five seconds. The platform processes this telemetry to detect issues such as high temperature, empty rooms with lights on, poor air quality, and abnormal humidity.

## IoT Architecture

The project follows a layered IoT architecture. This makes the system easy to understand and explain.

### 1. Perception Layer

The perception layer is represented by Python virtual devices. These devices simulate sensors for:

- Temperature
- Humidity
- Occupancy
- Light level
- Air quality
- Battery level
- Device status

No physical hardware is used. Sensor values are generated by Python using realistic ranges and occasional abnormal values.

### 2. Network Layer

The network layer uses MQTT. Devices publish messages to an MQTT broker. The project uses HiveMQ Public Broker by default because it is simple for demonstration and does not require local installation.

The network behavior is modeled as IEEE 802.15.4 / Zigbee-like communication. The simulator adds packet loss, random delay, RSSI, link quality, energy consumption, and battery drain.

### 3. Processing Layer

The processing layer is implemented in `processing/subscriber.py`. It subscribes to all telemetry topics using the wildcard:

```text
campus/+/+/+/telemetry
```

It validates each message, rejects incomplete or invalid data, calculates derived values, and evaluates alert rules.

### 4. Application Layer

The application layer is represented by a Node-RED Dashboard. The dashboard can show:

- Latest temperature
- Latest humidity
- Latest occupancy
- Latest alert text
- Temperature chart over time

## Wireless Communication Choice and Comparison

The selected wireless communication model is **IEEE 802.15.4 / Zigbee-like**.

### Why Zigbee-like?

Smart campus room sensors usually send short messages at regular intervals. They do not need high bandwidth. Many of them may be battery-powered, so energy efficiency is important. IEEE 802.15.4 and Zigbee-like systems are suitable for this kind of low-data-rate indoor IoT network.

The simulator represents Zigbee-like behavior using:

- Packet loss rate
- Random network delay
- RSSI
- Link quality
- Estimated energy consumption per message
- Battery drain after each transmission

### Comparison with Wi-Fi and LoRaWAN

| Feature | Zigbee-like / IEEE 802.15.4 | Wi-Fi | LoRaWAN |
|---|---|---|---|
| Range | Short to medium indoor range | Medium indoor range | Very long range |
| Power consumption | Low | Higher | Very low |
| Data rate | Low to moderate | High | Very low |
| Best use | Sensor networks in buildings | High-bandwidth devices | Outdoor wide-area sensing |
| Suitability for this project | High | Medium | Low to medium |

Wi-Fi is easy to deploy and has high data rate, but it consumes more power than Zigbee-like communication. LoRaWAN is excellent for long-range outdoor deployments, but it is not the best match for indoor room-level monitoring where frequent local telemetry is needed. Zigbee-like communication is the best fit for this simulated campus scenario.

## Device Simulation Design

The simulator is implemented in:

```text
simulator/device_simulator.py
```

The configuration is stored in:

```text
simulator/config.json
```

The simulator creates four virtual devices:

1. `classroom_101`
2. `lab_201`
3. `office_301`
4. `server_room_401`

Each device generates telemetry every five seconds. The values are randomized within realistic ranges. Some rooms have slightly different behavior. For example, the server room can generate higher temperatures to test high-temperature alerts.

### Telemetry Fields

Each message contains:

- `deviceId`
- `building`
- `room`
- `timestamp`
- `temperature`
- `humidity`
- `occupancy`
- `light_level`
- `air_quality`
- `battery_level`
- `status`
- `wireless`

The `wireless` object contains the Zigbee-like simulation values.

### Battery and Energy Simulation

Each successful transmission consumes simulated energy and decreases the battery level. The purpose is not to create an exact electrical model, but to demonstrate an important IoT concept: wireless communication has an energy cost.

## MQTT Topic Design and Payload Format

The MQTT topic hierarchy is:

```text
campus/{building}/{room}/{deviceId}/telemetry
```

Example:

```text
campus/main_building/classroom_101/classroom_101/telemetry
```

This hierarchy is useful because it organizes messages by campus, building, room, and device. It also supports wildcard subscriptions. The subscriber can receive all telemetry messages using:

```text
campus/+/+/+/telemetry
```

### Example Payload

```json
{
  "deviceId": "classroom_101",
  "building": "main_building",
  "room": "classroom_101",
  "timestamp": "2026-06-24T12:00:00+00:00",
  "temperature": 25.4,
  "humidity": 55.2,
  "occupancy": 18,
  "light_level": 72.5,
  "air_quality": 65.7,
  "battery_level": 95.8,
  "status": "OK",
  "wireless": {
    "model": "IEEE 802.15.4 / Zigbee-like",
    "packet_loss_rate": 0.05,
    "random_delay_ms": 180,
    "link_quality": 92,
    "rssi": -61,
    "estimated_energy_consumption_mwh": 0.018
  }
}
```

## Processing Logic and Rules

The subscriber is implemented in:

```text
processing/subscriber.py
```

It subscribes to:

```text
campus/+/+/+/telemetry
```

### Input Validation

The subscriber validates:

- Required fields exist.
- Field types are correct.
- Occupancy is not negative.
- Battery level is between 0 and 100.
- Humidity is between 0 and 100.
- Timestamp format is valid.
- Topic name follows the project naming policy.

If a message is missing fields, the subscriber rejects it and prints a validation message.

### Derived Values

The subscriber calculates:

| Derived Value | Description |
|---|---|
| `comfort_index` | Simple value based on temperature and humidity |
| `occupancy_status` | `EMPTY` or `OCCUPIED` |
| `abnormal_temperature_flag` | True when temperature is above 35 |
| `air_quality_status` | `GOOD`, `MODERATE`, or `POOR` |

### Alert Rules

| Alert | Condition |
|---|---|
| High temperature | `temperature > 35` |
| Empty room with lights on | `occupancy = 0` and `light_level > 60` |
| Poor air quality | `air_quality > 120` |
| Abnormal humidity | `humidity > 80` |
| Low battery | `battery_level < 20` |

These rules are intentionally simple so the project remains understandable and easy to explain.

## Security and Reliability Considerations

Although this is a simulation project, basic security and reliability controls are included.

### Security Controls

1. **Input validation:** The subscriber rejects invalid or incomplete payloads.
2. **Topic naming policy:** The subscriber accepts only the expected MQTT topic format.
3. **Sanitized logs:** Values are cleaned before printing to reduce log injection risk.
4. **Optional MQTT credentials:** The configuration file includes username and password fields for private brokers.
5. **Limited topic structure:** The system uses a predictable topic hierarchy instead of arbitrary topics.

### Reliability Considerations

1. **Packet loss simulation:** The simulator can skip messages to represent wireless packet loss.
2. **Random delay:** Each device transmission includes a random delay.
3. **Battery drain:** Repeated transmissions reduce simulated battery level.
4. **Disconnection handling:** The subscriber prints disconnection events.

For a real deployment, additional controls would be required, such as TLS, authenticated devices, persistent storage, access control, and monitoring of broker availability.

## Testing and Results

Testing is documented in:

```text
tests/test_cases.md
```

### Test Case 1: Normal Telemetry

The subscriber and simulator are started. The expected result is that the subscriber receives messages and prints `[DATA]` lines. This confirms that MQTT publish/subscribe and JSON processing work correctly.

### Test Case 2: Missing Field

A manual MQTT message is published with only partial data. The subscriber should reject the payload and print a validation error. This confirms that required field validation is working.

### Test Case 3: Abnormal Temperature

A message with `temperature = 38` is published. The subscriber should print:

```text
[ALERT] server_room_401: High temperature
```

This confirms that the high temperature rule works.

### Test Case 4: Broker Disconnection

The broker connection is interrupted or the broker host is changed to an invalid address. The expected result is that the application reports connection failure or disconnection. This confirms that the system can show network-related failure states during testing.

### Result Summary

| Test | Expected Result | Status |
|---|---|---|
| Normal telemetry | Data accepted and processed | Pass when broker is reachable |
| Missing field | Payload rejected | Pass |
| Abnormal temperature | Alert printed | Pass |

## Challenges and Limitations

The main challenge is balancing realism with simplicity. A real Zigbee network includes routing, channel interference, mesh topology, device association, and detailed physical layer behavior. This project models only the most important educational aspects: packet loss, delay, RSSI, link quality, energy use, and battery drain.

Another limitation is the use of a public MQTT broker. A public broker is useful for demonstration, but it should not be used for sensitive real data. In a production system, a private broker with authentication, authorization, and TLS would be required.

The dashboard is intentionally simple. It focuses on live monitoring rather than historical analysis. A more advanced system could store telemetry in a database and support reports, predictions, and long-term trends.

## Conclusion and Future Work

This project demonstrates a complete IoT system without using physical hardware. Python virtual devices simulate smart campus sensors. MQTT provides lightweight publish/subscribe communication. The subscriber validates data, calculates analytics, and prints alerts. Node-RED Dashboard provides a visual interface for live monitoring.

The selected Zigbee-like model is suitable for indoor smart campus sensors because it supports low-power short-message communication. The comparison with Wi-Fi and LoRaWAN shows that Zigbee-like communication is the most appropriate choice for this scenario.

Future improvements could include:

- Storing telemetry in SQLite, InfluxDB, or PostgreSQL.
- Adding a custom web dashboard.
- Using TLS and authenticated MQTT clients.
- Adding device registration and access control.
- Creating predictive analytics for temperature and air quality.
- Simulating more rooms and building-level aggregation.
